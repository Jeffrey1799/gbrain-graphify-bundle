GBrain 知识大脑

源仓库：github.com/garrytan/gbrain | 主要贡献者：Garry Tan (Creator)，Claude，clarajohan，Harshaldorlikar，pkyanam

一个由 AI 自动打理的项目知识库——解决「代码写了就忘」「人走了知识也走了」的问题。

什么是 GBrain？一句话说清楚

GBrain = 一个能搜你笔记的本地搜索引擎 + 知识库。

你往里面丢 Markdown 笔记，以后就能用中文搜到。它不是一个代码生成器或项目管理工具——它就是你团队的第二大脑。

它解决什么问题？
  • 同事离职了，代码逻辑和架构决策没人说得清
  • 三个月前修过一个 Bug，现在又遇到，得从头排查
  • 每个新人都要花几周才能摸清项目全貌
  • 技术文档写是写了，但没人看，也搜不到
核心价值
之前之后
"这个模块为什么这么设计？" → 去问人→ 直接搜大脑，秒出答案
"这个 Bug 以前修过吗？" → 翻 Git log→ 大脑自动记录，下次直接命中
新同事上手 → 啃文档 + 问人→ AI 自动分析项目，写进大脑
想法和经验 → 写个笔记吃灰→ 说给 AI 听，自动存进大脑
能做什么
  • 搜技术笔记、架构决策
  • 记录踩坑经验
  • 让 AI 理解项目上下文
  • 新员工快速上手
不是什么
  • 不是代码生成器
  • 不是项目管理工具
  • 不是 CI/CD
  • 不是在线服务——数据本地存储

GBrain 终端具体操作指令与用法

在日常使用中，在控制台中直接敲命令来管理您的知识库。以下是最核心的常用操作指令及其用法：

核心认知：如果您已经将 GBrain 接入了 AI Agent（如 Codex 或 Claude Code），这些终端指令您统统不需要掌握与手动执行！AI Agent 会在后台自动调用对应指令。您只需通过最自然的日常语言（如 “帮我查一下以前串口死锁是怎么修的” 或 “记下刚才的踩坑教训”）与 AI Agent 进行对话，由 AI 完成指令调用，即可完成知识的大脑存取（详见 与 AI Agent 配合 章节）。

1. 全文检索 (离线关键词搜索，最常用)

直接检索 GBrain 数据库中包含该字词的所有文档，无需 API 密钥，完全单机离线可用：

gbrain search 双击

2. 概念模糊查询 (需要配置 API 密钥)

利用向量模型进行语义上的匹配。即使笔记里没出现您搜索的字，只要意思相近也能匹配到：

gbrain query 物理红点采样优化

3. 精准读取特定笔记

若已知笔记的唯一标识名（Slug），可直接拉取并打印其 Markdown 全文内容：

gbrain get project_overview

4. 写入或更新特定笔记

通过标准输入或重定向指定文件，将 Markdown 内容保存或更新到大脑对应 Slug 中：

gbrain put project_overview < overview.md

5. 导入外部源文件 (Ingest)

将各种源文件（如音视频转录稿、论文 PDF、会议纪要等）导入并生成结构化笔记：

gbrain ingest meeting_transcript.txt --type transcript

6. 同步本地文件与数据库

将本地 Markdown 文件修改同步回本地数据库索引：

gbrain sync

快速开始：一条 One-Shot Prompt 全自动安装 GBrain + Graphify

Codex、Claude Code、Google Antigravity、WorkBuddy、Cursor 与 VS Code 均可使用下方 统一 One-Shot 提示词。安装器会按当前宿主写入本地 stdio MCP；独立 CodeBuddy 不在支持范围内。

发送给你的 AI Agent (Codex / Claude Code / Antigravity / WorkBuddy / Cursor / VS Code)

我要安装 GBrain 和 Graphify。请读取仓库 https://github.com/Jeffrey1799/gbrain-graphify-bundle 的 README，按指引操作。

克隆仓库后使用根入口：Windows 运行 .\bootstrap.ps1 -Agent codex，macOS/Linux 运行 bash ./bootstrap.sh --agent codex。bootstrap 随后会从当前 checkout 执行内部 gbrain-graphify-setup 工作流。

标准的 3 步全自动接入工作流：
  1. 步骤 1：发送 One-Shot 提示词 — Agent 自动完成环境检测、依赖自愈 (Python 3.10+/Bun)、GBrain 与 Graphify 安装及 stdio MCP 配置。只有显式指定时才使用镜像。
  2. 步骤 2：重启 Agent 会话 — 安装完成后，重启一次 Agent 会话（或新建对话框），使系统挂载的 MCP 连接器正式生效。
  3. 步骤 3：一键构建 GBrain 项目大脑 & Graphify 代码图谱 — 打开具体项目工作区，发送以下指令，Agent 将全自动生成 Graphify AST 代码图谱（运行 graphify extract . --code-only 生成 graphify-out/graph.json），并在 ~/brain/projects/<项目名>/ 蒸馏生成 GBrain 架构与决策脑库，自动运行 gbrain sync： 
    /project-knowledge-bootstrap 读取 https://github.com/Jeffrey1799/gbrain-graphify-bundle 并按 project-knowledge-bootstrap 指引，为当前工作区构建项目知识大脑与代码图谱。
正式支持：Codex、Claude Code、Google Antigravity、WorkBuddy、Cursor 与 VS Code。默认只写用户级 MCP；只有指定 --workspace 才写项目规则。
已有安装的恢复命令

根 bootstrap 是唯一安装入口。预检报告固定版本不一致或 MCP 冲突时，先检查现有安装，再只携带必要的显式授权参数重跑：

.\bootstrap.ps1 -Agent codex -Upgrade
.\bootstrap.ps1 -Agent codex -ReplaceConflicts
bash ./bootstrap.sh --agent codex --upgrade
bash ./bootstrap.sh --agent codex --replace-conflicts

可将 codex 替换为 claude、antigravity、workbuddy、cursor 或 vscode。损坏的 JSON 不会被覆盖，必须先修复或恢复该文件。

AI Agent：

死锁 Bug 分析

现象
连上串口 → 断开 → 再次连接，串口看起来打开了但没有任何数据流，游戏不响应。

根因（v0.0.56）
代码直接把 port.readable 转移（transfer） 给了 Web Worker：

// 错误做法 v0.0.56
const readable = selectedPort.readable;
worker.postMessage({ type: 'START_SERIAL', readable }, [readable]);

postMessage 的第二个参数 [readable] 会把 readable 流转移到 Worker 线程，主线程侧永久失去该流的锁。当调用 port.close() 时，主线程等待 readable 解锁 → Worker 持有锁 → 死锁。

修复（v0.0.57）
插入一个 TransformStream 中转通道，主线程持有 passthrough 的控制权：

// 正确做法 v0.0.57
const passthrough = new TransformStream<Uint8Array, Uint8Array>();
serialPipeClosedRef.current = readable.pipeTo(passthrough.writable).catch(() => {});
worker.postMessage(
  { type: 'START_SERIAL', readable: passthrough.readable },
  [passthrough.readable]
);

关键改动：

  • 主线程把 readable pipe 到 passthrough.writable，保留 pipe 的 Promise
  • 只把 passthrough.readable 转移给 Worker
  • 关闭前 await serialPipeClosedRef.current 确保 pipe 完全排空

教训
永远不要直接把 port.readable 转给 Worker。 用 TransformStream 做中转，主线程保留生命周期控制权。每次 close 前要等待 pipe 排空。

[Source: git commit fba31c5, c93c977]

验证结论：项目大脑构建完成后，AI 通过 mcp__gbrain__search 调用 GBrain 语义检索，命中 projects/trackpoint-game/pitfalls 页面，返回 evidence: "high_vector_match"（向量相似度 0.90）。说明向量模型参与了检索，知识已被成功索引并可查询。

与 AI Agent 配合：Brain-First 模式

核心认知：从“手动检索”到“自动协同”

GBrain 本质上是一套强大的知识库构建与检索工具。如果您只是在命令行里由人类手动运行（例如手动敲 gbrain search / gbrain query 等命令调用），那它充其量只是一个本地的个人 Wiki 工具，在写代码的过程中频繁切换和复制粘贴，开发体验是割裂的。

真正释放 GBrain 威力的秘诀，在于将其接入 AI Agent（如 Codex / Claude Code 等）。通过让 AI 替代人在后台自动执行读写和匹配，GBrain 被无缝融入到了您的日常 AI 辅助开发工作流中。此时，GBrain 变为了 AI 的“外挂硬盘”与“经验缓存区”——AI 替你检索、AI 替你沉淀，人机协同的效率自此呈指数级上升。

数据安全：GBrain 默认所有数据存在本地硬盘，基础功能不需要联网。只有启用语义搜索（配置 OpenAI Embedding）或远程数据库（Supabase）时才有网络请求。

一旦接入，这就是 GBrain 最有价值的工作方式——AI Agent 每次回答问题前，会先查 GBrain，有了项目上下文再给出答案：

你问问题
"这个 API 超时怎么优化？"
→
Brain-First 查找
先搜大脑有没有相关笔记
→
结合上下文回答
笔记 + 代码 = 更准的答案

核心协作关系：AI Agent 工作流中的四大角色

在一个基于知识库的 AI 协作开发流程中，许多人容易混淆不同的技术概念。以下是它们在工作流中的清晰分工和定位：

技术组件 扮演的角色 (比喻) 核心作用 / 职责 在实战流中的具体表现
AI Agent
（如 Codex / Claude Code）		 执行官 (大脑外肢与工具箱) 直接与用户交互，读取您的指令并拆解为任务，调用终端工具（如读取文件、运行测试、读写数据库等）来自动干活。 当您对它说 “查一下关于小红点双击的原理”，AI Agent 就会自动去调用 GBrain 进行查询，并将查回的笔记整合输出。
GBrain
(本地引擎与数据库)		 本地档案室 (知识库本体) 存放所有技术笔记、设计文档及架构理解的本地物理档案库。提供高并发的本地读写、分词过滤和数据库存储服务。 负责安全、私密地将您生成的项目 Markdown 笔记（如 .gbrain-md/）实时持久化到 GBrain 本地数据库中。
向量模型
(如 ZeroEntropy / OpenAI embedding)		 翻译官 (语义特征提取器) 将 GBrain 里的自然语言文档和代码翻译成高维空间的“语义指纹（Embedding 向量）”，使 GBrain 内部能够进行概念层面的相似性关联。 当 AI Agent 想要跨语言/概念查文档时（如用中文“双击”去配对“double click”），向量模型能让 GBrain 轻松实现模糊语义查找。
LLM 大模型
(如 Claude 3.5 Sonnet / Gemini Pro)		 决策大脑 (逻辑推理中心) 提供强大的逻辑分析、代码理解、总结归纳与文字生成能力。负责对获取的信息进行推理和整合。 当 GBrain 查出相关笔记、代码片后，大模型会对这些原材料进行逻辑拼接、避坑提炼，并生成最终通俗、高含金量的解答发给您。
一句话总结协作流：
您命令 AI Agent 去工作 ➡️ AI Agent 自动向 GBrain 档案室 调阅文档 ➡️ 向量模型 帮 GBrain 实现模糊语义匹配，抓出最相关的笔记 ➡️ LLM 大模型 对这些笔记进行深度逻辑梳理，最终把提炼后的最佳方案呈献给您。

常见问题

Windows 安装时提示 Git SSL 连接重置怎么解决？

现象：git clone 时报 schannel: SSL connection reset 或 Failed to receive handshake, SSL/TLS connection failed。

原因：Windows 的 Schannel SSL 后端通过代理（如 127.0.0.1:7897）与 GitHub 握手会失败。

解法：克隆时临时绕过代理：git -c http.proxy="" clone https://github.com/garrytan/gbrain.git ~/gbrain --depth 1。

Windows 上 Bun 全局安装 bun install -g 会崩溃怎么办？

现象：bun install -g github:garrytan/gbrain 在 tarball 提取阶段崩溃或 gbrain doctor 报告 schema_version 为 0。

原因：Bun 在 Windows 上对全局安装的 postinstall 脚本支持不稳定，schema migrations 未自动执行。

解法：改用确定性安装路径——git clone 源码后本地构建：git clone ... && cd ~/gbrain && bun install && bun link。

GBrain 的数据安全吗？会不会泄露到外网？

基础功能完全本地运行。当前使用 PGLite（嵌入式本地 Postgres），所有数据存储在 ~/.gbrain/brain.pglite，没有网络请求。

  • 安装时 git clone 和 bun install 有网络请求（一次性）
  • 配置了 ZeroEntropy API Key 后，嵌入模型调用时有数据出站（仅文本片段）
  • 没有配置远程数据库（Supabase），数据不会上传到云端
需要 API 密钥吗？用哪家的？

基础功能（关键词搜索 gbrain search、存笔记）不需要 API Key。

如果要启用语义检索（gbrain query），GBrain 默认使用 ZeroEntropy 的 zembed-1 嵌入模型（1280 维）和 zerank-2 重排模型。需要配置 ZEROENTROPY_API_KEY 环境变量。

也可切换到 OpenAI 的嵌入模型，但当前实测 ZeroEntropy 方案工作正常。

什么是"语义检索"？和 search.mode 是什么关系？

语义检索（API Key） 决定能否进行模糊语义匹配——搜"小红点"能查到"TrackPoint"，不需要关键词完全一致。

search.mode 决定每次检索拿多少上下文和 Token 预算，和是否有 API Key 无关：

  • conservative：4K token，10 个片段，最省 Token
  • balanced（推荐）：12K token，25 个片段，Sonnet 级性价比
  • tokenmax：无预算上限，50 个片段，最全面

两者正交。没 API Key 也能换 search.mode；有 API Key 也能选 conservative。

笔记存数据库了，怎么用文本编辑器看？

GBrain 数据库（PGLite）是二进制的，不能直接用编辑器打开。但我们的 prompt 要求了 Write-Through——创建 brain page 的同时也会写出 .md 文件到 ~/brain/projects/<项目名>/ 并提交到 Git。

所以你可以：

  • 搜知识：对 AI 说"搜一下项目 XXX" → AI 查数据库
  • 看原文：直接打开 ~/brain/projects/<项目名>/*.md → 文本编辑器

如果某个笔记只有数据库里有、仓库里没有，可以运行 gbrain sync --push 同步到仓库。

多个项目怎么隔离？

当前使用的是单脑拓扑（Topology 1）——所有项目共享同一个 PGLite 数据库。通过命名空间隔离：

  • 项目 A 的知识 → projects/project-a/*
  • 项目 B 的知识 → projects/project-b/*

如果希望完全独立的数据库实例，可以使用分裂引擎拓扑（Topology 3）：用 GBRAIN_HOME 环境变量为每个项目创建独立的 PGLite 实例。

大脑里的数据能导出吗？

能。有两种方式：

  • 通过仓库：~/brain/ 本身就是 Git 仓库，所有 .md 文件可以直接复制、提交、分享
  • 通过命令：gbrain get <slug> 打印 Markdown 全文，可以重定向到文件
  • 通过 MCP：用 list_pages 列出所有页面 + get_page 逐篇读取
gbrain doctor 在 Windows 上运行报错？

现象：gbrain doctor --json 输出为空，或提示 PGLite lock timeout。

原因：Bun 在 Windows 上对大 JSON 输出处理不稳定，且 MCP 连接时 PGLite 被占用。

解法：

  • 通过 MCP 调用 run_doctor 工具获取完整健康报告
  • 或断开 MCP 后单独运行 gbrain doctor
如何升级 GBrain？

我们使用的是 git clone 安装方式，升级步骤：

cd ~/gbrain && git pull origin master && bun install
gbrain apply-migrations --yes
gbrain post-upgrade

然后运行 gbrain doctor（通过 MCP run_doctor）验证健康状态。

如果使用 bun install -g 安装，升级命令是 gbrain upgrade。

如何在其他项目上复用项目大脑？

只需要复制 prompt 即可。在新项目的 AI Agent 中发送「项目大脑」章节的优化版提示词，AI 会自动：

  1. 扫描新项目的代码结构和 Git 历史
  2. 在 GBrain 中创建 projects/<新项目名>/* 页面
  3. 同步 .md 文件到 ~/brain/projects/<新项目名>/
  4. 验证检索效果

不需要重新安装 GBrain 或重新配置 MCP。

Graphify 项目知识图谱

官方仓库：github.com/Graphify-Labs/graphify | 官方 PyPI 包：graphifyy（命令仍为 graphify）

什么是 Graphify？一句话说清楚

Graphify = 把当前项目里的代码与文档关系，构造成一张持久化知识图谱。

它通过 AST 解析函数、类、调用、导入、继承和依赖关系，再把 Markdown、PDF、图片等非代码资产中的概念、设计理由与代码连接起来。构建完成后，AI 不必每次从头遍历整个仓库，而可以先查询图谱，再按证据定位源文件。

图中的“事实”和“推断”如何区分？

Graphify 会给关系标记证据级别。阅读结果时应优先相信直接从源材料中提取的关系，并对推断关系进行源代码复核：

标记含义使用建议
EXTRACTED关系直接存在于源代码、文档或显式引用中。可作为高置信线索，但重要修改前仍应打开源文件确认。
INFERREDGraphify 根据命名、解析和上下文推导出的关系。适合发现隐藏连接，不应当作开发者意图的直接证明。
AMBIGUOUS存在多个可能匹配，无法唯一确定。必须结合文件路径、符号定义、调用点 and 测试人工消歧。

Graphify 与 GBrain：互补，而不是替代

核心区别：GBrain 更像“长期知识档案室”，Graphify 更像“当前项目结构地图”。前者擅长保存经验与笔记，后者擅长呈现代码、文档和组件之间的关系。

只装 Graphify 时

你会获得一张高质量的项目结构图，适合当前代码库理解、关系查询和影响分析；但历史 Bug 教训不会凭空出现，除非它们已写在代码注释、文档、提交说明或由 Agent 提炼的 Markdown 中。

Graphify 提供“项目现在长什么样”，GBrain 保存“过去为什么这样做、踩过什么坑”。Agent 可以先查长期经验，再用图谱定位当前实现与影响路径。

阶段优先动作目的

工具用途

实战案例：Native 层与 UI 层如何通信？

以下是一次真实测试记录——构建项目图谱后，直接向 AI 提问验证图谱+MCP 查询效果：

User： TrackPointCaptureHelper 和 UI 层之间是怎么通信的？
AI Agent：

[MCP-First 流程] 先查 Graphify MCP：query_graph BFS depth=2 → 132 节点，定位到 TrackPointCaptureHelper（98 条边）、serial.worker.ts（deg 18）、OfficeScene.tsx（deg 16）。再用 shortest_path 发现 4 跳路径，get_node/get_neighbors 查看各节点详情。

图谱没有 C# → TypeScript 的直接路径，因为这是跨进程动态 IPC。

通信架构：两条独立 IPC 通道

通道 1：双击捕获

C# TrackPointCaptureHelper.exe
  → stdout JSON
  → electron/trackpoint-capture.cjs (TrackPointCaptureController)
  → main.cjs: sendTrackPointDoubleClick()
  → IPC trackpoint:double-click
  → preload.cjs (contextBridge)
  → window.electronAPI.onTrackPointDoubleClick()
  → src/App.tsx

通道 2：原始输入帧

C# TrackPointCaptureHelper.exe (不同参数)
  → stdout JSON
  → electron/trackpoint-input.cjs (TrackPointInputController)
  → main.cjs: sendInputFrame() / sendInputStatus()
  → IPC trackpoint:input-frame / trackpoint:input-status
  → preload.cjs (contextBridge)
  → window.electronAPI.onInputFrame() / onInputStatus()
  → src/workers/serial.worker.ts

安全配置：contextIsolation: true，nodeIntegration: false（main.cjs:39-40），IPC 通道白名单控制。

[Source: 图谱先导定位关键文件，再读 main.cjs、preload.cjs、trackpoint-capture.cjs 验证]

User follow-up： 你再查一下你的项目大脑，TrackPointCaptureHelper 和 UI 层之间是怎么通信的？
AI Agent 回答：

[GBrain 检索] 查 gbrain 命中 projects/trackpoint-game（评分 0.90）、projects/trackpoint-game/code-modules（评分 0.86）。

[Graphify 图谱] 再次 query_graph 定位到 164 节点，get_neighbors("serial.worker.ts") 得到 18 个邻居。

信息来源有什么缺什么
GBrain项目结构、ADR 决策理由、踩坑历史IPC 通道名、preload API 签名、stdout JSON 协议
Graphify 图谱模块关系、函数调用、导入链跨进程动态 IPC 连接
源码精确的函数签名、IPC 通道名、安全配置需要图谱指引才知道看哪些文件

[Source: gbrain query + graphify query + 源码验证]

验证结论：图谱构建完成后，AI 通过 Graphify MCP 的 query_graph 定位关键节点，shortest_path 发现 TypeScript 侧连接，get_node/get_neighbors 查看详情。图谱没有 C# → TypeScript 的直接路径（动态 IPC 无法被 AST 捕获），因此进一步打开源码验证，确认了两条独立的 IPC 通道。整个过程体现了"图谱先缩小范围，源码确认细节"的 MCP-First 工作流价值。

团队协作与维护

推荐团队流程
  1. 由一名成员在干净工作区构建并验证图谱。
  2. 团队决定是否将 graphify-out/ 提交到 Git；官方设计允许共享图谱，让其他成员拉取后立即使用。
  3. 本地成本或临时文件按团队策略忽略，例如 graphify-out/cost.json。
  4. 代码提交后用 Git Hook 自动执行 AST 更新；文档、图片或 PDF 变化时执行语义 --update。
  5. 重大重构后重新验证核心 query/path，而不是只检查文件时间戳。

选择优点注意事项
提交到 Git全员共享同一张项目地图，新成员无需首次完整构建。需要约定更新责任、冲突处理和敏感信息审查。
仅本地生成仓库更轻，避免把生成物与内部路径带入远端。每位成员需要自行构建，图谱版本可能不一致。
建议：先在内部仓库试运行，审查 graph.json、报告和路径信息是否包含不应共享的数据，再决定是否纳入版本控制。

常见问题

安装时到底是 graphify 还是 graphifyy？

官方 PyPI 包名是 graphifyy（双 y），安装后提供的 CLI 命令仍然是 graphify，MCP 命令为 graphify-mcp。不要安装其他名称相近但无关的 PyPI 包。

代码分析需要 API Key 吗？

代码 AST 提取可以完全本地运行，不需要 API Key。文档、PDF、图片的语义提取会使用当前 AI Agent 的模型，或在 headless CLI 模式下使用你显式配置的模型后端。涉及内部资料时，应先确认数据出站规则。

为什么安装后找不到 graphify 命令？

uv tool 的可执行目录可能尚未加入当前 shell 的 PATH。运行 uv tool update-shell 后重新打开终端；当前会话也可以先使用 Agent 查到的绝对可执行路径进行验证。

Windows PowerShell 中为什么不能输入 /graphify .？

/graphify 是 AI Agent 内的 Skill 命令，不是 PowerShell 命令。PowerShell 里直接执行 CLI 应输入 graphify .。在 Codex 对话中则使用 $graphify .。

MCP 与 Graphify Skill 有什么区别？

Skill 负责读取工作区、调度提取、生成与更新图谱；MCP 加载已有 graph.json，为 Agent 提供结构化查询工具。通常先安装 Skill 并构图，再接入 MCP。MCP 不是构图前置条件。

中文分词依赖 jieba 安装失败怎么办？

在 Windows 上通过 uv tool install "graphifyy[mcp,chinese]==0.9.30" 安装时，jieba 可能因 uv 沙箱无法删除缓存文件或镜像源哈希不匹配而失败。

解决方法：先用 pip 从官方 PyPI 下载 jieba 并构建 wheel，再通过 uv tool install --with 注入。具体步骤：

pip install jieba --index-url https://pypi.org/simple --trusted-host pypi.org --trusted-host files.pythonhosted.org
# 找到缓存中的 wheel 路径
ls /c/Users/xxx/AppData/Local/pip/cache/wheels/*/*/*/jieba-*.whl
# 用 uv tool install --with 指定本地 wheel
uv tool install --force "graphifyy[mcp,chinese]==0.9.30" --with /path/to/jieba-0.42.1-py3-none-any.whl

也可暂时省略 chinese extra，之后按上述方法补充。

Windows Git Bash 中路径参数报错？

在 Git Bash 中传递绝对路径（如 /c/Users/xxx/project）给 graphify extract 等命令时，路径可能被错误拼接为 C:\c\Users\...。

解决方法：切换到目标目录后直接使用 . 作为路径参数，或使用完整 Windows 路径格式（含双反斜杠）并用引号包裹。

MCP 配置后 Agent 还是找不到 graphify-mcp？

修改 mcp.json 添加 graphify MCP 服务器后，当前 AI Agent 会话不会自动加载新的 MCP 服务器。需要重启 Agent 会话才能让 mcp__graphify__* 工具出现在工具列表中。这是平台机制限制，不是配置错误。

重新运行安装命令失败（Windows 沙箱）？

在 Windows 上重新运行 Graphify 平台集成命令时，可能因沙箱无法删除旧技能引用目录而报错 SAFE_DELETE_FAIL_CLOSED。

如果技能文件已存在且功能正常，此错误可安全忽略。如需重新安装，请先确认并清理当前平台对应的 Graphify skill 目录，再重新运行官方安装命令。

支持 PPTX 吗？

当前官方文件支持表明确列出了 DOCX、XLSX、PDF、图片和 Google Slides 快捷文件，但没有列出本地 PPTX 直接提取。建议让 Agent 先把 PPTX 转为 PDF或结构化 Markdown，再纳入 Graphify。

中文查询结果不理想怎么办？

安装 graphifyy[mcp,chinese]==0.9.30 以启用 MCP 服务与 jieba 中文分词；同时尽量在问题中包含真实类名、函数名、模块名或协议名。图查询后还应结合源文件复核。

如何更新 Graphify？

最稳妥的方式是再次运行本手册的“安装 Prompt”，让 Agent 按当前官方文档使用 uv tool install --force 更新同一组 extras。升级后重新注册 Skill，并重新执行 graphify hook install 刷新 Hook 中嵌入的解释器路径。

如何卸载？

graphify uninstall 可移除各平台集成；添加 --purge 会同时删除 graphify-out/。执行 purge 前应确认图谱是否已备份或提交。

图谱过期或查询不准确怎么办？

先运行 --update，再重复原始 query/path。若节点 ID 或 schema 与新版本不兼容、图文件损坏或大量文件规则变化，再考虑完整重建。不要用“命令执行成功”代替项目级查询验证。
